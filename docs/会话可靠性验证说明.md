# 会话可靠性验证说明

本验证对应《低空 Agent 项目优化计划｜行动清单与进度记录》的 P2 第 8 项，并为 P1 的故障注入、可观测性和 P3 的评测结果提供证据。
验证对象是最后一次已保存的跨轮上下文，以及它如何进入后续实际工具调用。不会把聊天历史、单轮 AgentState 和跨轮 Session 当作同一种数据。

## 环境与隔离

使用 [专用 Compose 配置](../docker/session_reliability.compose.yml)，不复用生产 Compose 项目或现有数据卷。

- 两个独立 Uvicorn 应用进程 `app_a`、`app_b`，使用同一个真实 PostgreSQL 16 和 Redis 7。
- 登录 `/agent/query` 使用 PostgreSQL Session；匿名 `/nl/parse` 使用 Redis，保持独立键前缀。
- PostgreSQL、Redis 使用专属临时命名卷，保留数据以验证进程重启，结束后删除该测试项目的卷。
- 网络为 Docker internal network，没有宿主机端口映射，也不调用外部模型或天气服务。
- LLM 关闭，采用规则解析。天气由同一内部网络中的确定性 HTTP 服务提供，应用仍执行真实 HTTP 请求、规则计算、历史保存和工具调用。
- 使用测试账户；JSON 证据中的 token、password、authorization 会被脱敏。

实现文件：

- [控制器](../scripts/session_reliability_eval.py)：启动环境、重启/终止服务、注入数据库故障、保存结果、清理资源。
- [HTTP 探针](../scripts/session_reliability_probe.py)：在 Linux 容器中发出真实 HTTP 请求，支持同时发出两条请求。
- [天气服务](../scripts/session_reliability_fixture.py)：返回固定天气条件，并可增加可控延迟以保证并发请求重叠。

应用、HTTP、数据库、Redis 和故障动作均为真实运行；天气业务数据是固定夹具。不能据此声称真实模型、真实天气供应商的延迟或质量。

## 场景与断言

每个场景按 `SR-场景名-重复序号` 编号，输出一份 JSON。表中的场景名与命令行 `--scenarios` 一致。

| 场景名 | 执行动作 | 主要检查 |
| --- | --- | --- |
| `multiturn` | 完整评估后依次修改城市和任务类型 | 每轮 PostgreSQL 上下文、回包和 Trace 中的实际工具输入一致 |
| `app_restart` | 保存缺地点的待补请求，重启应用，再补“深圳” | 原日期、时间和任务类型完整恢复，实际工具正确执行 |
| `app_kill` | 保存完成后强制 SIGKILL 应用，再启动 | 最后一次确认保存的待补上下文仍能续接 |
| `cross_instance` | 在 A 发起待补请求，在 B 补地点 | 恢复依赖真实共享存储，不依赖 A 的内存 |
| `postgres_restart` | 保存待补任务，重启 PostgreSQL，再续接 | 已提交会话保留，连接恢复后工具参数正确 |
| `postgres_outage` | 停止 PostgreSQL，发请求，再启动并续接 | 暂不可用明确返回 503，无额外天气调用，恢复后可继续 |
| `postgres_expiry` | 仅将目标会话截止时间改为两秒后，实际等待到期 | 旧日期/时间不被复用，不执行缺参工具，聊天历史保留 |
| `redis_expiry` | 对目标匿名会话使用真实 PEXPIRE，再等待到期 | 键消失；后续缺参查询返回 422，不假装记得已过期数据 |
| `redis_outage` | 停止 Redis，再发匿名续接、无 Session 请求和登录知识请求 | 匿名续接明确返回 503；无 Session 解析、PostgreSQL 会话不受影响；重启后匿名续接恢复 |
| `redis_restart` | 记录 AOF 配置，正常重启 Redis | 未过期匿名上下文保留并可继续解析 |
| `isolation` | 两用户同 ID 同时发起不同条件的请求，再分别修改；增加同用户新 ID | 不串用户/会话，其他用户无法读取 Trace，不因同 ID 错误阻塞另一用户 |
| `session_save_failure` | 用测试库触发器使目标 Session 写入报错 | 已提交建单结果返回，明确提示未保存会话，只产生一条任务，先前已确认上下文仍可恢复 |
| `concurrent_update` | 两实例对同用户同会话同时改城市、任务类型 | 一条执行，另一条明确 `SESSION_BUSY`；重试后保留两个修改 |
| `crash_before_session_write` | 测试触发器挂起 Session 写入，确认任务已提交，再 SIGKILL 应用 | 中断请求没有成功确认，重启不自动重建任务，先前已确认会话保留 |

数据库故障触发器仅存在于专用测试数据库，并在场景结束后删除。生产应用不包含天气夹具或数据库故障开关。

## 并发策略

同一用户、同一个非空 Session ID 的两条 Agent 请求不并行修改上下文。重叠请求立即返回业务失败 `SESSION_BUSY` 和 `retryable: true`，客户端应等待上一轮完成后再提交。
该结果沿用 `/agent/query` 的 HTTP 200 业务响应契约，因此统计时必须检查 `success` 和错误码，不能只看 HTTP 状态。

PostgreSQL 部署通过用户与 Session ID 生成稳定的 64 位键，使用非阻塞的会话级咨询锁，覆盖读取、合并、业务执行和 Session 回写。
业务中间可能提交事务，因此使用跨事务保持的会话级锁，正常结束显式解锁；数据库连接终止时 PostgreSQL 会释放相应锁。[PostgreSQL 锁函数](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)

不同用户或不同 Session ID 不互相阻塞。SQLite/TTLCache 开发环境使用进程内互斥，不声称该分支具备跨实例并发保护。
匿名解析的并发合并策略不在本轮验收范围内。

数据库连接池开启 `pool_pre_ping`，以替换从池中取出的失效连接。这只能处理取连接时的失效情况，不能自动恢复已经中断的事务，也不会自动重跑已执行的业务。[SQLAlchemy 连接池说明](https://docs.sqlalchemy.org/en/20/core/pooling.html#disconnect-handling-pessimistic)

## 指标口径

| 指标 | 分母与判定 |
| --- | --- |
| 场景通过数 | 每个编号场景的所有断言通过；报告通过数/执行数，不能用单个成功请求代替整场景成功 |
| 会话恢复成功数 | 仅计未过期且先前已确认写入的可恢复会话；后续请求成功且关键参数正确才算恢复 |
| 字段正确数 | 统计 `field:` 断言的正确项/检查项：包括实际工具结果、Trace 中 `tool_call.input_summary`、匿名解析地点和并发后的数据库字段 |
| 过期处置 | 应追问时追问、不执行缺参工具；不纳入“应恢复会话”的分母 |
| 隔离违规 | 检查跨用户同 ID、同用户不同 ID 的字段和访问权限；单个违规即失败 |
| 重复副作用 | 故障前后按用户核对任务数量；同一次请求的内部故障恢复不得额外建单 |
| 并发一致性 | 同会话一条执行、一条明确拒绝；拒绝请求重试后，城市和任务类型均正确 |
| 恢复时间 | 控制器发起故障到收到首条正确续接响应，包含重启、就绪等待和依赖恢复，不包含之后取 Trace 的时间 |
| 续接延迟 | Linux HTTP 探针发起续接请求到收到回包的单调时钟耗时；与 `agent_runtime.timings` 分开保留 |
| 请求及工具统计 | 分别统计成功、追问、降级、会话忙、HTTP 错误和连接中断；工具统计仅包括回包中实际拿到的工具结果 |

工具结果统计不覆盖进程强杀时未返回/未提交的事件，不能把这些缺失记录记作成功。
每类不足 20 个恢复样本时，脚本只保留样本、中位数和最大值，`p95` 为 null，避免用很少样本包装稳定的尾延迟结论。
固定用例中的 100% 和零违规是本批验收结果，不是生产 SLA 或统计可靠性承诺。

`crash_before_session_write` 的原始 `recovery_ms` 从发起建单计时至重启后完成数据库核验，未执行续接请求。它是重启与现场核验耗时，单独解释，不与其他场景的续接恢复时间合并。

## 运行与留档

从仓库根目录运行。先构建包含当前应用和脚本的镜像；已有依赖缓存时也可复用本地验证基础镜像。

```powershell
docker build -t drone-low-altitude-agent:session-reliability-validation .
python scripts/session_reliability_eval.py --repeats 3
```

只跑部分场景：

```powershell
python scripts/session_reliability_eval.py --repeats 3 --scenarios app_restart app_kill cross_instance
```

默认原始结果在 `data/eval-reports/session-reliability/<测试项目名>/`：

- `report.json`：配置、镜像 ID、代码基线、关键源文件 SHA-256、逐场景结果和汇总。
- `SR-*.json`：每次 HTTP 请求/响应、会话快照、实际工具输入所在的 Trace、进程动作和数据库故障点。
- `container-logs.txt`：仅本测试项目的容器日志。

运行结束默认清理临时容器、网络和专属卷。`--keep` 可保留现场，之后使用同一个 Compose 文件与项目名清理：

```powershell
docker compose -f docker/session_reliability.compose.yml -p session-reliability-实际项目名 down --volumes
```

原始结果目录由 `.gitignore` 排除；仓库中的实测报告及精简证据需从已完成的结果提取，不能手工伪造指标。
如需严格比较改动前后的性能，应固定相同镜像配置、请求、重复次数和故障动作，单独执行性能实验。

2026-11-21 已完成结果见 [会话可靠性实测报告](会话可靠性实测报告.md) 与 [留档证据](evidence/session-reliability-20261121/README.md)。

## 边界

- 本轮恢复的是已保存的跨轮字段，不恢复进程崩溃前正在执行的 Python 调用栈。
- 业务已提交但 Session 尚未写入时被杀进程，可能只保留先前上下文；系统不自动重放建单。没有因此实现客户端重试的幂等键。
- 正常重启 Redis 的结果不能外推为强杀、断电或所有 AOF 落盘策略下的零丢失。异常退出的丢失窗口需要另测。[Redis 持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- 未覆盖宿主机断电、磁盘损坏、主从切换、高并发容量、所有网络分区及长时间生产流量。
- 认证或依赖读取阶段就失败的 HTTP 请求可能尚未进入 Agent Run；进程强杀前缓冲但未提交的 Trace 也可能不存在。用控制器记录、容器日志和数据库快照说明现场，不补造 Trace。
