# 会话可靠性实测报告

实测日期：2026-11-21。对应行动清单 P2 第 8 项，关联 P1 第 4、5 项及 P3 第 9 项。

本轮在隔离 Docker 环境中运行两个真实应用进程、PostgreSQL 和 Redis，验证跨轮字段在重启、过期、存储中断、并发修改和后置保存失败时的行为。修复后三轮共 **42/42 场景通过，24/24 个应恢复会话成功续接，288/288 项关键字段检查正确**。这是固定场景的验收结果，样本规模不支持生产 SLA 推断。

## 基线复现及修复

修改前单轮执行 14 类场景，10/14 通过；应恢复会话 8/8，字段检查 91/94。恢复成功与整场景通过的分母不同：存储恢复后能续接，不代表中断时的错误响应也符合契约。[基线摘要](evidence/session-reliability-20261121/baseline-summary.json)

| 失败用例 | 真实现象 | 本轮修复 |
| --- | --- | --- |
| `SR-postgres_outage-1` | PostgreSQL 停止时返回笼统 500；恢复后仍可续接 | 数据库 `OperationalError` 明确映射 503、`DATABASE_UNAVAILABLE` |
| `SR-redis_outage-1` | 匿名会话依赖 Redis，停止后返回笼统 500 | Redis 错误明确映射 503、`SESSION_STORAGE_UNAVAILABLE` |
| `SR-isolation-1` | PostgreSQL 重启后，B 实例第一次请求复用失效连接而失败，后续缺少该轮上下文 | 连接池启用 `pool_pre_ping`；日志中的 `AdminShutdown` 支持连接失效诊断，此例不是已证明的数据串用 |
| `SR-concurrent_update-1` | 同用户同会话同时改城市、任务类型，两条均成功，最后城市退回深圳，丢失广州修改 | 在读上下文之前获取按用户和会话划分的非阻塞执行锁，覆盖合并、工具执行和 Session 写入；重叠请求返回 `SESSION_BUSY`，重试后保留两个修改 |

[基线失败断言与请求摘录](evidence/session-reliability-20261121/baseline-failures.json) 和 [基线容器日志](evidence/session-reliability-20261121/baseline-container.log) 保留了定位依据。

PostgreSQL 使用跨事务保持的会话级咨询锁，适配业务中途提交事务的行为；不同用户同 ID 不共用锁。SQLite/TTLCache 分支仅提供进程内保护。数据库连接失效处理不自动重放业务，客户端重复建单的幂等键也不属于这次改动。[实现及运行说明](会话可靠性验证说明.md#并发策略)

## 最终三轮结果

每一类场景独立重复 3 次。完整断言、预期值、实际值和原始文件哈希见 [最终摘要](evidence/session-reliability-20261121/final-summary.json)。

| 场景名 | 结果 | 验证的业务行为 |
| --- | --- | --- |
| `multiturn` | 3/3 | 深圳评估 → 改广州 → 改测绘；每轮持久化上下文、实际工具参数和 Trace 一致 |
| `app_restart` | 3/3 | 待补任务保存后重启应用，补地点仍保留日期、时间和任务类型 |
| `app_kill` | 3/3 | 已保存后 SIGKILL 应用再启动，可继续待补任务 |
| `cross_instance` | 3/3 | A 保存，B 续接，实际工具参数正确 |
| `postgres_restart` | 3/3 | PostgreSQL 重启后已提交上下文可读，实际工具继续执行 |
| `postgres_outage` | 3/3 | 中断时明确 503，没有额外天气请求；恢复后继续 |
| `postgres_expiry` | 3/3 | 仅目标记录加速到期；缺参继续追问，历史记录保留 |
| `redis_expiry` | 3/3 | 真实键到期删除，后续缺参返回 422 |
| `redis_outage` | 3/3 | 匿名续接 503；无 Session 解析和登录知识查询可用；Redis 启动后匿名会话恢复 |
| `redis_restart` | 3/3 | Redis 正常重启后未过期上下文保留并可继续解析 |
| `isolation` | 3/3 | 两用户同 ID 并发执行且互不串用，同用户新 ID 不继承地点，跨用户读取 Trace 返回 404 |
| `session_save_failure` | 3/3 | 建单已提交、Session 保存失败时保留业务结果和警告，仅增加一条任务；旧上下文可恢复 |
| `concurrent_update` | 3/3 | 同会话并发只准入一条，另一条明确拒绝；重试后广州和测绘同时保留 |
| `crash_before_session_write` | 3/3 | 确认建单提交且 Session 写入阻塞后强杀应用；请求连接中断，重启不自动重复建单，旧上下文仍在 |

恢复指标的 24 个样本来自应用重启、应用强杀、跨实例、PostgreSQL 重启/中断、Redis 中断/重启、Session 写入失败，共 8 类 × 3 次。过期会话和未获保存确认的崩溃中请求不纳入该分母。

字段指标统计名称以 `field:` 开头的断言，包括实际评估工具结果、Trace 中实际工具输入、匿名解析地点和并发后数据库字段。它是逐字段正确数，不是 288 个独立会话。

隔离场景 3/3 通过，检查范围内未发现串用或越权。建单保存失败与写入前崩溃共 6 次注入，均只新增一条任务，未出现内部自动重放造成的重复。没有据此承诺客户端再次提交相同建单请求也能去重。

## 恢复时间与请求延迟

下表为控制器发起故障至收到正确续接响应的时间，包含 Docker 操作、启动、就绪探测和依赖恢复。它衡量本机测试恢复过程，不等于 Agent 单次处理耗时。每类只有 3 个样本，报告中 `p95` 为 null。

| 故障 | 样本数 | 中位数 ms | 最大值 ms |
| --- | --- | --- | --- |
| 应用正常重启 | 3 | 5781 | 5969 |
| 应用 SIGKILL 后启动 | 3 | 5984 | 6187 |
| PostgreSQL 重启 | 3 | 2484 | 2531 |
| PostgreSQL 停止、故障请求、再启动 | 3 | 4250 | 6172 |
| Redis 停止、独立性检查、再启动 | 3 | 5297 | 5406 |
| Redis 正常重启 | 3 | 2047 | 2140 |

原始报告在 `crash_before_session_write` 的 `recovery_ms` 中另存了 7812、7969、8344 ms。该计时从发起建单开始，直到重启后完成任务数和旧上下文核验，包含故障点等待与数据库检查；未执行续接请求，因此不与上表的恢复时间合并。

容器内 HTTP 探针另行记录续接请求延迟。例如应用重启场景为 227.767、229.205、268.352 ms，跨实例为 260.539、166.236、153.095 ms。完整样本保留在 `by_scenario.continuation_latency_ms`。本轮没有执行相同样本数的性能优化前后实验，不给出性能提升百分比。

## Trace 如何支持验收

实际请求可通过 `trace_id` 关联解析、上下文合并、计划、工具输入/结果、阶段计时和最终业务状态。已提交的 Trace 通过已有接口读回，并写入证据文件；测试账户和数据库已清理，离线复核应使用这些 JSON。

- 正常续接例：`SR-app_restart-1`，Trace `d741f4ac-89ec-4542-9c7e-0277bd8f1787`，工具输入保留原日期、14:00–15:00、巡检及本轮补入的深圳；最终 `outcome=success`。[完整证据](evidence/session-reliability-20261121/SR-app_restart-1.json)
- 后置保存失败例：`SR-session_save_failure-1`，Trace `cec83ffe-117c-4837-a841-50802e52fcea`，工具成功，`session_write` 的 `ok=false`，最终 `outcome=degraded` 且有保存失败警告；数据库任务增量为 1，旧上下文未覆盖。[完整证据](evidence/session-reliability-20261121/SR-session_save_failure-1.json)
- 并发例：`SR-concurrent_update-1`，两实例同时提交不同修改，一条成功、一条业务错误 `SESSION_BUSY`；拒绝请求在前一轮结束后重试，最终数据库为广州、测绘。[完整证据](evidence/session-reliability-20261121/SR-concurrent_update-1.json)
- 崩溃例：`SR-crash_before_session_write-1` 记录真实 `pg_stat_activity` 中的 `PgSleep`、已提交任务数、SIGKILL 和旧上下文快照。进程被杀前未提交的最终 Trace 可能不存在，使用控制器和存储证据说明现场。[完整证据](evidence/session-reliability-20261121/SR-crash_before_session_write-1.json)

本批 `/agent/query` 请求共 93 次，按互斥类别统计如下；匿名 `/nl/parse` 和 Trace 查询不在此分母中。

| 业务/传输结果 | 次数 |
| --- | --- |
| 成功，无警告 | 51 |
| 缺参追问 | 30 |
| 成功但 Session 保存降级 | 3 |
| 同会话忙，明确拒绝 | 3 |
| HTTP 错误：PostgreSQL 暂不可用 | 3 |
| 强杀导致连接中断 | 3 |

返回到客户端的工具结果为 54 个，成功 54、失败 0，`fallback_used` 计数为 0。这里注入的是工具之后的存储故障及依赖/进程中断，不能用此数字证明工具对任意故障都成功，也不能把强杀时没有返回的工具结果计入成功分母。`SESSION_BUSY` 和追问均可为 HTTP 200，必须结合业务字段判断。

已有阶段计时可区分 Parser、Planner、工具、天气 HTTP、规则、快照和 Session 保存；`duration_ms` 与 `self_ms` 避免把嵌套阶段重复相加。`processing_ms` 的范围在对话和 Trace 最终提交之前，完整 HTTP 延迟以探针值为准。LLM 关闭，本轮没有真实模型阶段耗时样本。
