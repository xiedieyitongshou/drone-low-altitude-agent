# Day156 线上轻量压测报告

## 1. 测试结论

本次 Day156 在服务器本机执行轻量压测，未通过 SSH 隧道压测 HTTP 流量。压测目标为服务器本机后端 `http://127.0.0.1:8000`，用于验证当前私有部署环境的真实承载能力。

首次测试结论：

- 3 VU 轻量压测下，HTTP 层稳定：111 个请求，HTTP failed rate 为 0。
- 容器状态稳定：后端、前端、Redis 均保持 healthy，重启次数均为 0。
- 未发现 `SQLite database locked`、Traceback、5xx、Redis OOM 或容器重启。
- 只读接口表现很好，P95 均低于 15 ms。
- 写入/评估接口表现可接受，`/cruise/evaluate` P95 约 355.53 ms。
- Agent 链路是主要耗时来源，`/agent/query` P95 约 6048.89 ms。
- Agent 业务检查存在 7 次 `success != true`，但 HTTP 状态均为 200，需要后续结合 Agent Trace 分析是解析失败、业务降级还是脚本断言过严。
- 当前服务器配置可以支撑低并发私有演示。建议演示并发控制在 1 到 3 人，暂不建议开放公网高并发访问。
- 本轮没有证据表明 SQLite 已成为瓶颈，暂不触发 PostgreSQL 强制迁移，但继续保留迁移预案。

同步后复测结论：

- 服务器已同步到 GitHub `main` 最新 commit `5ea91c9`，并强制重建后端容器。
- 容器内已确认包含 `f98bd6c` 的 `normalize_confidence` / `confidence_labels` 修复。
- 3 VU 轻量 baseline 复测后，HTTP failed rate 仍为 0。
- 业务检查恢复为 100% 通过：138/138 passed，`agent query success` 为 30/30 passed。
- 之前 7 次 `success != true` 已确认是服务器部署版本落后导致的 LLM parser `confidence` 字段兼容问题，不是压力、SQLite 或 Redis 瓶颈。
- 最终判断：当前服务器可支撑 1 到 3 人低并发私有演示；主要风险转为 LLM 链路耗时波动，而不是基础服务容量。

## 7. 瓶颈判断

只读接口不是瓶颈：

- `/health`、`/tasks`、`/agent/traces/{trace_id}` 的 P95 都低于 15 ms。
- 查询类接口在 3 VU 下没有明显延迟或错误。

SQLite 暂未表现为瓶颈：

- 写入相关 setup task 创建成功。
- `/cruise/evaluate` P95 约 355.53 ms。
- 日志未发现 `database locked`。
- 容器没有重启，系统资源没有打满。

Agent 链路是当前主要瓶颈：

- `/agent/query` P95 约 6.05 s，显著高于其它接口。
- 31 次 Agent HTTP 请求均返回 200，但 7 次业务 `success` 字段不为 true。
- 这更像 Agent 业务链路、解析、上下文、工具调用或降级策略问题，而不是 HTTP 服务、Redis 或 SQLite 的容量问题。

## 8. 当前演示承载建议

当前私有演示环境建议：

- 单人演示：可支撑。
- 1 到 3 人并发轻量演示：可支撑。
- 5 到 10 人并发：需要另跑 Day156 扩展档位，并重点观察 Agent 业务成功率。
- 20 到 50 并发：当前阶段不建议在该服务器和 SQLite 配置上直接执行。

演示时建议：

- 避免多个用户同时连续触发 Agent 对话。
- 演示前先跑 smoke test 验证健康状态。
- 演示中优先展示结构化评估、任务查询、Trace 查询等稳定链路。
- Agent 对话作为核心能力展示，但需要保留失败降级解释。

## 9. 后续动作

已完成：

- 已抽取首次测试中 7 次 `agent query success` 失败对应的 Conversation/Trace。
- 已确认失败原因是服务器部署版本落后，缺少 `f98bd6c` 的 LLM parser `confidence` 字段兼容修复。
- 已同步服务器代码、重建后端容器并完成复测，`agent query success` 恢复为 30/30 passed。

建议后续补充：

1. 增加 5 VU / 120s 的轻量扩展档，只在低峰执行。
2. 在压测脚本中为 Agent 业务失败记录响应摘要或 Trace ID，便于定位。
3. 增加压测数据清理脚本，按 `load_user_*`、`load_smoke_*`、`RUN_ID` 清理任务、会话和 Trace。
4. PostgreSQL 迁移验证暂不强制启动，等出现 SQLite lock、写入 P95 明显上升或演示并发需求超过 3 人后再触发。
