# 设计取舍说明

本文档说明项目中几个关键工程决策。目标是让安全边界、可测试性、部署成本和演示价值之间的取舍清楚可解释。

## 规则引擎 vs LLM

适飞 / 慎飞 / 禁飞判断必须稳定、可复现、可测试，所以由确定性规则引擎负责。LLM 只用于自然语言解析、字段补全、表达润色和解释增强，不能直接生成或覆盖安全结论。

这样设计的收益：

- 同一输入在同一规则版本下得到一致结果。
- 测试可以覆盖具体阈值、规则命中和边界条件。
- 出现争议时可以追溯到规则、天气数据和 trace。
- LLM 失败时可以回退到规则解析或固定模板输出。

## RAG vs 规则结论

RAG 只用于补充操作建议、SOP 提示和政策边界说明，不改变规则引擎输出的适飞结论。

原因：

- 知识库召回可能为空、低置信或过期。
- RAG 语料不应被包装成权威监管结论。
- 飞行安全判断应来自明确规则和可验证数据。
- 空召回或低置信时应返回保守说明，而不是编造政策依据。

## 自然语言入口 vs 结构化接口

`/agent/query` 提供自然语言统一入口，适合真实用户交互和演示。结构化接口继续保留，适合自动化测试、前端直接调用、第三方系统集成和故障定位。

取舍结果：

- 自然语言入口负责交互体验。
- 结构化接口负责稳定集成和可测试性。
- Agent Runtime 调用业务服务，不绕过结构化能力。

## TTLCache vs Redis vs Database Memory

项目通过统一会话记忆接口隔离底层实现：

- TTLCache：适合本地单进程开发，启动成本低。
- Redis：适合 Docker 联调和多实例共享短期上下文。
- Database Memory：适合持久化会话上下文和历史审计。

默认建议：

- 本地开发：`SESSION_MEMORY_BACKEND=ttlcache`
- Docker 联调：`SESSION_MEMORY_BACKEND=redis`

## SQLite vs PostgreSQL

SQLite 适合本地运行、功能验证和面试演示，部署简单、迁移成本低。生产级高并发写入、备份恢复、权限治理和连接池管理更适合 PostgreSQL。

当前选择 SQLite 的原因：

- 项目重点是 Agent 工程能力和业务闭环，不是数据库基础设施。
- 本地和 Docker 演示可以快速启动。
- Alembic migration 已经保留了后续迁移到 PostgreSQL 的路径。

边界：

- SQLite 不适合高并发写入。
- 生产部署需要 PostgreSQL、备份、连接池、监控和迁移流程。

## Eval fast vs full

Eval 分为快速门禁和完整评测：

- Fast Eval：适合每次 push/PR 自动执行，覆盖核心回归指标。
- Full Eval：适合手动触发或阶段验收，生成完整 Markdown / JSON 报告。

这样设计的原因：

- CI 需要速度和稳定性，不能依赖慢速外部服务。
- 完整报告适合分析趋势和准备展示，但不应拖慢每次提交。
- Agent 行为退化需要可量化指标，而不是只靠人工试用。

## 前端权限边界

前端只负责展示权限和交互入口，不作为安全边界。所有用户身份、角色判断、数据过滤和管理员权限都以后端 token 解析和服务层校验为准。

原因：

- 前端传入的 `user_id` 不可信。
- 页面隐藏按钮不能替代后端鉴权。
- 管理员接口必须在后端强制校验 `role`。
- 历史、Trace、知识库、任务单都需要后端按用户和租户过滤。

## Docker 默认 Agent Loop

Docker 部署默认使用：

```env
AGENT_RUNTIME_MODE=loop
```

`legacy` 仅作为本地兼容模式和 Agent Loop 异常 fallback 路径，不作为 Docker 主链路。这样可以确保部署演示走真实 Agent Runtime，而不是回退到旧的串行流程。
