# 任务版本控制与过期结果处理

2026-11-24：任务行使用单调递增的 `version`，防止取消被旧评估覆盖，以及新地点或时间误用旧条件的评估结果。

## 写入约定

数据库迁移 `d8a4c6e1f025` 为 `mission_tasks` 新增非空整数 `version`；已有任务从 1 开始。后端默认在启动时补齐迁移。任务列表、详情和新建任务响应返回版本。版本属于整条任务，状态未变而内容改变时也会递增。

以下 HTTP 写入口必须在 JSON 中携带读取任务时的 `expected_version`：

| 入口 | 其他请求内容 |
|---|---|
| `PATCH /tasks/{id}` | 待修改字段 |
| `PATCH /tasks/{id}/status` | `status` |
| `POST /tasks/{id}/evaluate` | 无 |
| `POST /tasks/{id}/preflight-check` | 无 |
| `POST /tasks/{id}/recommend` | 可选 `scan_hours`、`min_window_hours` |
| `POST /tasks/{id}/select-window` | `rank` 或显式 `window` |

例如，读取到版本 5 后取消：

```json
{"status": "cancelled", "expected_version": 5}
```

缺少版本返回 HTTP 428、`TASK_VERSION_REQUIRED`；版本不匹配返回 HTTP 409、`TASK_VERSION_CONFLICT`。非法版本值仍通过请求校验返回 422。前端与后端应一起更新；旧客户端需要先读取任务再提交版本。

同一数据库的所有后端实例应使用新版本代码，避免旧代码绕过版本条件。Docker 部署需要用更新后的代码重建镜像。

SQLAlchemy `version_id_col` 在普通 ORM 更新时自动递增版本，并把原版本加入 UPDATE 条件。不在各入口手动加一。任务更新不得通过不带版本条件的批量 UPDATE 或原生 SQL 绕过此约束。内部服务允许没有客户端版本的调用，但仍捕获读取时版本并接受数据库 CAS 保护；公开 HTTP 写入口一律要求版本，Agent 使用后端绑定的版本。

## 长任务与事务

评估、复核和推荐先读取并校验任务，复制请求参数和版本，再释放只读事务并调用天气服务。保存时重新读取任务，与计算开始时的版本比较；随后由 ORM 原子更新再次防住“最后一次读取之后又发生修改”的窗口。

任务更新、版本递增、评估/天气快照和直接写入的复核 Trace 在同一事务内完成。任何版本冲突都回滚本次写入，不留下悬空的成功评估。计算响应中 `request.input_task_version` 表示计算使用的任务版本，`request.task_version` 表示成功应用后的任务版本；历史请求 JSON 也记录输入版本。

取消不等待旧天气请求完成。取消先提交成功时，旧评估只能失败，不能恢复任务；如果另一项更新先成功，持旧版本的取消也会冲突，刷新后再由用户发起操作。已经取消后再次取消可直接确认当前取消状态，不再次递增版本。已经完成的任务不会因此被重新打开。

## 当前结果与历史

地点、日期、起止时间、任务类型、目的或候选地点发生实际变化时，任务回到草稿，清除当前结论、当前评估/Trace/会话指针、推荐、选定窗口及复核摘要。重新排回草稿同样清理当前结果。历史评估、天气、对话和 Trace 本身不删除，仍可复盘。

改名称等不影响评估输入的字段时保留已完成结果，但会递增任务版本，使仍在执行的旧操作冲突。更新用户 metadata 时不能伪造服务器管理的最新推荐或复核摘要。选择窗口后清除此前的当前评估与复核结论，避免将旧窗口的评估视为新窗口结论。

## Agent 与客户端

Agent 从成功的任务工具结果提取 `current_task_version`，与任务 ID 一起存入 Session。推荐窗口同时绑定 `last_recommendation_task_id`，防止切换任务或天气失败后重试时沿用另一个任务的排名。工具版本只来自后端上下文或任务读取，不使用模型生成的数字。旧会话缺少推荐版本或窗口归属时不能直接按排名选窗口，需要重新推荐。

带操作 ID 的 Agent 任务请求还会冻结第一次执行绑定的任务 ID、工具动作和版本。即使业务已提交、后续回复处理中断，同一操作 ID 的重试也不能静默换成新版本再应用一次。版本冲突作为不可自动重试的本轮结果保存，直接返回用户，不执行 legacy 兜底。清理旧版本和窗口上下文后，用户可以发起新的推荐或评估。

前端始终提交当前页面读取的版本。冲突后刷新任务并提示用户，不自动重放旧动作；Agent 的终止冲突结束原操作，新的用户操作使用新操作 ID。前端并行跟踪评估与取消，不阻止用户在评估期间取消；收到较早版本的详情或结果时不覆盖较新状态，取消后的晚到评估结果不作为当前结果展示。

历史建单幂等快照可能没有版本，回放时返回 `version=null`，不伪造当前版本。新任务写操作必须先通过任务详情取得有效版本。

## 验收

`tests/test_mission_task_versioning.py` 使用 SQLite 临时库；设置专用 `IDEMPOTENCY_TEST_DATABASE_URL` 后，在 PostgreSQL 每例独立随机 schema 中执行并清理。用例覆盖评估/复核/推荐期间取消或修改、最后读取与 UPDATE 之间的竞争、两个短写入口并发、快照写入故障回滚、关键字段失效与历史保留、HTTP 版本契约、旧排名选择、Agent 冲突终止与回复中断后的旧版本重试。天气与推荐使用固定夹具，不调用真实天气或 LLM。

`frontend/tests/taskVersion.test.mjs` 验证晚到评估及无版本历史响应不会作为当前结果应用；其余前端静态检查与构建继续执行。

2026-11-24 补充 `frontend/e2e/task-cancellation.spec.ts`：Chromium 实际点击任务页面，验证评估期间可取消、晚到冲突后刷新、晚到旧成功响应不成为当前结果、晚到旧列表刷新不覆盖取消后的新列表，以及正常评估仍可显示。测试发现并修复了旧列表响应可能使列表回到“已评估”、详情仍为“已取消”的竞争；列表请求现以递增编号拒绝过时响应。页面详情/列表、按钮、提示、请求版本及无自动写重放均有断言。该层使用 HTTP 夹具；数据库取消状态与快照原子性由 PostgreSQL 专项验证。运行方式为 `cd frontend` 后执行 `npm run test:e2e`；详见 [CI 门禁](CI-CD说明.md#前端-ci)。
