# 负载测试说明

## 1. 测试目标

本方案对应 Day154：负载测试方案设计。

目标不是把演示服务器压垮，而是用可复现数据回答三个问题：

- 当前部署在单用户演示、多人同时查看、短时集中调用下是否稳定。
- SQLite、Redis、FastAPI、容器资源和 SSH 隧道分别可能成为哪些瓶颈。
- 是否已经达到需要迁移 PostgreSQL 或调整部署拓扑的触发条件。

## 2. 当前部署前提

当前线上演示环境按私有部署处理：

- 前端绑定服务器本机 `127.0.0.1:5173`。
- 后端绑定服务器本机 `127.0.0.1:8000`。
- Redis 绑定服务器本机 `127.0.0.1:6379`。
- 默认通过 SSH 隧道从本地访问 `http://localhost:5173` 和 `http://localhost:8000`。

SSH 隧道适合连通性验证和轻量演示，不适合直接作为正式压测通道。原因是压测结果会混入本地网络、SSH 加密转发和客户端机器性能，不能代表服务器本体性能。

因此本方案区分两类测试：

| 类型 | 执行位置 | 访问地址 | 目的 |
| --- | --- | --- | --- |
| 隧道 smoke test | 本地开发机 | `http://localhost:8000` | 验证 SSH 隧道下基本链路可用 |
| 服务器本体压测 | 服务器本机或同内网测试机 | `http://127.0.0.1:8000` | 评估 FastAPI、SQLite、Redis 和容器资源表现 |

Day155 编写脚本时，默认应优先支持服务器本机执行。

## 3. 工具选择

优先使用 `k6`：

- 脚本轻量，适合 HTTP API 压测。
- 支持阶段式并发、阈值、JSON summary。
- 对求职项目展示足够清晰。

备选使用 `Locust`：

- 适合复杂用户行为建模。
- 当需要长时间 Web UI 化观察或更复杂任务流时再引入。

当前阶段不建议同时引入两套工具，避免压测体系本身复杂化。Day155 先落 `k6`。

## 4. 测试模式

### 4.1 后端本体模式

环境建议：

```text
LLM_ENABLED=false
NL_PARSER_MODE=rule
WEATHER_PROVIDER_MODE=sample 或 mock
```

目的：

- 排除大模型限流、外部天气 API 延迟和第三方服务波动。
- 只测本项目后端、数据库、Redis、规则引擎、Agent Runtime 和 Trace 写入能力。

这是判断 SQLite 是否继续可用的主要依据。

### 4.2 真实演示链路模式

环境建议：

```text
LLM_ENABLED=true
NL_PARSER_MODE=hybrid
```

目的：

- 验证面试演示路径在真实依赖开启时的用户体验。
- 观察 LLM 和天气 API 外部依赖带来的尾延迟、限流和失败率。

该模式只做轻量验证，不把外部服务限流算成本项目后端性能瓶颈。

## 5. 接口场景

### 5.1 健康检查

接口：

```http
GET /health
```

用途：

- 测基础 HTTP 服务、容器反应速度和无数据库写入的基线。
- 作为所有压测开始前的预检查。

建议占比：`10%`。

### 5.2 登录

接口：

```http
POST /auth/login
```

用途：

- 测认证查询、密码校验和 JWT 生成。
- 为后续需要鉴权的接口准备 token。

建议占比：独立小场景测试，不混入高频主场景，避免把密码哈希成本误判为业务链路成本。

### 5.3 Agent 对话

接口：

```http
POST /agent/query
```

用途：

- 测自然语言解析、Agent Loop、工具选择、会话记忆、Conversation History、Trace 写入。
- 这是最能代表项目 Agent 能力的核心压测场景。

示例请求：

```json
{
  "session_id": "k6-session-${VU}",
  "query": "深圳湾明天上午9点到11点可以进行无人机巡检吗"
}
```

建议占比：`35%`。

### 5.4 单地点评估

接口：

```http
POST /cruise/evaluate
```

用途：

- 测结构化评估入口、规则引擎、评估结果落库、天气样例读取或 mock 数据链路。
- 这是判断 SQLite 写入压力的核心场景之一。

示例请求：

```json
{
  "location": "深圳湾",
  "date": "2026-08-27",
  "start_time": "09:00",
  "end_time": "11:00",
  "task_type": "inspection",
  "purpose": "低空巡检"
}
```

建议占比：`25%`。

### 5.5 任务单查询

接口：

```http
GET /tasks?page=1&page_size=20
GET /tasks/{task_id}
```

用途：

- 测登录用户的数据隔离查询、分页查询和任务详情聚合。
- 观察 SQLite 在读多写少场景下的表现。

建议占比：`20%`。

### 5.6 Trace 查询

接口：

```http
GET /agent/traces/{trace_id}
```

用途：

- 测 Trace 明细读取、用户权限过滤和长链路排障数据查询。
- 需要先通过 `/agent/query` 生成有效 `trace_id`，再作为压测输入数据。

建议占比：`10%`。

## 6. 负载档位

| 档位 | 并发用户 | 持续时间 | 目的 |
| --- | ---: | --- | --- |
| smoke | 1 | 1 分钟 | 确认脚本、账号、token、接口和数据可用 |
| demo | 1 到 3 | 5 分钟 | 模拟单场面试演示 |
| small-team | 5 到 10 | 10 分钟 | 模拟多人同时访问演示 |
| upper-demo | 20 到 50 | 10 分钟 | 探测轻量服务器边界 |
| spike | 0 到 50 突增 | 2 到 5 分钟 | 观察短时突发和恢复能力 |

执行顺序必须从低到高。只要低档位出现持续 5xx、容器重启、SQLite lock 激增或服务器资源耗尽，就停止更高档位。

## 7. 关键指标

k6 侧记录：

- QPS / request rate
- 平均响应时间
- P95 / P99
- HTTP 4xx / 5xx 错误率
- 请求超时数
- 各接口单独耗时分布

服务器侧记录：

- CPU 使用率
- 内存使用率
- 磁盘剩余空间
- Docker 容器状态和重启次数
- 后端容器日志中的异常数量
- Redis 连接状态和内存占用
- SQLite `database is locked`、写入失败、慢查询迹象

推荐观察命令：

```bash
docker compose ps
docker stats
docker compose logs --tail=200 app
df -h
free -h
top
```

Redis 检查：

```bash
docker compose exec redis redis-cli ping
docker compose exec redis redis-cli info clients
docker compose exec redis redis-cli info memory
```

SQLite 重点观察：

- 是否出现 `database is locked`。
- `/agent/query`、`/cruise/evaluate`、任务单写入接口是否 5xx 增加。
- 写入类接口 P95 是否明显高于只读接口。

## 8. 初始阈值

这些阈值用于 Day155/Day156 的第一版基线，不等同生产 SLA。

| 场景 | P95 | P99 | 错误率 |
| --- | ---: | ---: | ---: |
| `/health` | <= 200 ms | <= 500 ms | <= 0.1% |
| `/auth/login` | <= 800 ms | <= 1500 ms | <= 1% |
| `/cruise/evaluate` 后端本体模式 | <= 1500 ms | <= 3000 ms | <= 1% |
| `/agent/query` 后端本体模式 | <= 2000 ms | <= 4000 ms | <= 1% |
| 任务单和 Trace 查询 | <= 1000 ms | <= 2000 ms | <= 1% |

真实演示链路模式允许 P95 更高，但要把 LLM、天气 API 超时和后端自身错误分开记录。

## 9. PostgreSQL 迁移触发条件

满足任一条件时，进入 Day157-Day159 的 PostgreSQL 迁移预案验证：

- 5 到 10 并发下，写入类接口稳定出现 SQLite lock。
- 20 并发以内，`/agent/query` 或 `/cruise/evaluate` 错误率持续超过 `1%`，且日志指向数据库写入竞争。
- Trace、Conversation History、任务单同时写入时，P95 长期超过 `3000 ms`，且 CPU/内存未满，瓶颈集中在 SQLite。
- 演示数据量增长后，任务单列表、Trace 查询、历史查询出现不可接受延迟。
- 需要多后端实例部署或更可靠的备份恢复机制。

如果压测瓶颈来自 LLM 限流、天气 API 延迟、SSH 隧道、前端资源加载或服务器 CPU/内存不足，不能直接归因到 SQLite。

## 10. 数据准备

压测前准备：

- 创建低权限压测用户，不使用管理员账号。
- 准备固定测试密码，通过服务器私有 `.env` 或 k6 环境变量传入，不写入 Git。
- 预置若干任务单，用于 `/tasks` 和 `/agent/traces/{trace_id}` 查询。
- 预置或生成若干 trace_id，用于 Trace 查询场景。
- 使用样例天气数据或 mock provider，避免真实天气 API 被压测打爆。

压测后清理：

- 删除压测用户产生的任务单、Conversation、Trace 和评估历史。
- 如使用演示库，压测前先备份，压测后恢复 demo seed。
- 压测报告只提交脱敏指标，不提交真实 token、真实 IP、真实账号密码。

## 11. SSH 隧道下的执行策略

本地通过 SSH 隧道只做 smoke test：

```powershell
curl.exe http://localhost:8000/health
```

如果需要用 k6 走隧道，限制为低并发：

```powershell
k6 run -e BASE_URL=http://localhost:8000 -e MODE=smoke scripts/load/k6-smoke.js
```

不建议通过 SSH 隧道执行 20 到 50 并发压测。正式压测应在服务器上执行：

```bash
k6 run -e BASE_URL=http://127.0.0.1:8000 -e MODE=backend scripts/load/k6-api.js
```

这样结果更接近服务端真实承载能力。

压测数据隔离方案：

- 用户名统一使用 `load_smoke_*` 和 `load_user_*` 前缀，且包含 `RUN_ID`，不复用管理员账号或真实演示账号。
- 固定输入使用深圳湾、2026-08-27、09:00 到 11:00、`inspection` 等样例值，`purpose` 和 task metadata 写入 `load baseline`/`run_id` 标记。
- 测试密码通过 `LOAD_TEST_PASSWORD` 环境变量覆盖，默认值只用于本地低权限临时用户，不写入真实 token。
- 压测后按用户名前缀、`session_id` 前缀、task metadata `run_id` 清理任务单、Conversation、Trace 和评估历史；演示库压测前先备份，必要时恢复 demo seed。

## 14. 报告格式

每次压测至少记录：

- 测试日期和执行人。
- Git commit hash。
- 部署模式：本地、服务器本机、SSH 隧道、Docker Compose。
- 环境变量摘要：是否开启 LLM、是否使用 mock 天气、数据库类型。
- 服务器规格：CPU、内存、磁盘。
- 负载档位：并发、持续时间、接口权重。
- k6 指标：QPS、平均响应、P95、P99、错误率。
- 服务器指标：CPU、内存、容器重启、Redis、SQLite 异常。
- 结论：当前是否支撑演示、瓶颈是什么、是否触发 PostgreSQL 迁移验证。

## 15. 风险边界

- 不在公开仓库记录真实公网 IP、真实 SSH 用户名、真实私钥路径、真实账号密码和 token。
- 不对公网真实入口做高并发压测，避免触发云厂商风控或影响其他服务。
- 不把 LLM 和天气 API 的外部限流作为后端性能退化证据。
- 不使用管理员账号做压测主账号。
- 不在面试演示窗口执行压测。
- 不把压测产生的脏数据长期留在演示数据库。
